## Context

当前插件存在三个 bug：插件路径解析、选项缩进格式和自定义选项格式。这些都是实现 bug，不影响架构或引入新依赖。

## Goals / Non-Goals

**Goals:**
- 修复插件路径解析，支持相对路径跨项目复用
- 修复选项缩进逻辑，确保所有选项行应用模板缩进
- 统一自定义选项格式，确保与前置选项一致

**Non-Goals:**
- 不修改 OpenCode 插件加载机制（我们控制的是插件注册路径，不是加载器）
- 不改变用户配置文件格式或引入新配置项
- 不影响已使用绝对路径注册的用户

## Decisions

### Decision 1: 插件路径解析修复方案

**选择方案**：修改 postinstall 脚本的插件注册逻辑，使用项目根目录相对路径而非用户配置中的字符串直接传递。

**理由**：
- OpenCode 插件加载器期望绝对路径或相对于 OpenCode 配置文件位置的路径
- 用户配置 `.opencode/plugins/opencode-lark-bridge` 是相对于项目根目录
- 当用户在其他项目中使用相同配置时，相对路径仍然有效
- 修复点在 postinstall 的路径解析，而非插件代码本身

**替代方案**：
- 强制要求用户使用绝对路径 → 拒绝：破坏跨项目复用性
- 在插件代码中动态解析路径 → 拒绝：增加复杂度，且插件代码在加载前无法执行

### Decision 2: 选项缩进修复方案

**选择方案**：修改 `question-mapper.ts` 中的选项列表生成逻辑，在替换 `{options}` 变量时，检测模板缩进并应用到所有选项行。

**理由**：
- 现有 spec 要求"所有选项行应用相同缩进"
- 当前实现只在第一个选项行应用缩进，后续行丢失
- 需要解析模板中 `{options}` 前的缩进字符串，然后在拼接选项时为每行添加相同缩进

**替代方案**：
- 硬编码缩进格式 → 拒绝：破坏模板自定义能力
- 在模板变量替换后重新格式化 → 拒绝：性能差且可能破坏用户自定义格式

### Decision 3: 自定义选项格式统一方案

**选择方案**：修改 `question-mapper.ts`，将 `{suffix}` 内容格式化为与 `{options}` 相同的列表项格式（带 `•` 前缀和缩进）。

**理由**：
- 用户报告"自定义输入"选项与前置选项对齐不一致
- 现有 `{suffix}` 变量只处理 `(可自定义输入)` 等文本，未格式化为列表项
- 需要在生成选项列表时，检测 `custom: true` 并将 suffix 内容追加为最后一个选项

**替代方案**：
- 在模板中单独处理 `{suffix}` → 拒绝：用户需要手动对齐，体验差
- 保持现状 → 拒绝：格式不一致，用户体验受损

## Risks / Trade-offs

**Risk 1**: 路径解析修改可能影响现有绝对路径用户 → **缓解**：向后兼容，绝对路径和相对路径都支持

**Risk 2**: 选项缩进修复可能影响现有自定义模板 → **缓解**：缩进逻辑只处理模板定义的缩进，不破坏用户自定义格式

**Risk 3**: 自定义选项格式修改可能破坏现有 `{suffix}` 用法 → **缓解**：仅在 `custom: true` 时格式化为列表项，其他情况保持原样
